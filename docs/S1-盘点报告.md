## 2. UI 粗糙点清单（S2 重设计输入）

### 2.1 全局性

1. **无导航**：tabbar 被删未补，app 页面图不连通（见 1.1）——S2 第一优先级：设计底部导航与页面信息架构。
2. **emoji 当图标**（📚📖📊📝⏱️⚙️📅🎉▶⏸⏹）：全部图标位用 emoji，跨端渲染不一致、与"博物馆"气质完全不符。
3. **配色单一悬浮**：全站 `#667eea→#764ba2` 紫色渐变（按钮/进度条/整页背景/计时页满屏渐变），无品牌色系、无色彩层级；深底页（计时/统计）文字对比度未校。
4. **无设计变量**：各页硬编码 rpx/色值，无主题 token，S2 需建立设计系统基线。
5. **死链与空态混用**：center 菜单 4 个死链接（note/list、activity/my、reading/records、user/settings 均未注册）；空态图 `/static/default-cover.png`、`/static/empty.png`、`/static/default-avatar.png` 均不存在（裂图）。
6. **目标值三处不一致**：后端 goal=30、首页默认 30、个人中心硬编码 60 分钟。

### 2.2 逐页

- **首页**：目标卡信息密度低（已读/目标/百分比三层重复表达）；"近期活动/最新笔记"是永远为空的假模块（无后端域支撑）——S2 需决策砍掉或补域；开始阅读按钮占屏过大（padding 40rpx 的通栏大按钮）。
- **详情页**：评分区 `48rpx` 大数字无视觉锚点；简介无折叠/展开；操作栏只有单按钮，无"边读边记"等读书场景动作；缺出版社/ISBN/分类等已有字段的展示（表里有没显示）。
- **书架页**：Tab 无数量角标；卡片进度条 12rpx 过细且无分段刻度；无排序/筛选；无批量操作；空态无引导动作（应引导去选书——但选书入口本身不存在）。
- **计时页**：满屏渐变背景 + 纯文字计时，无氛围感设计；暂停时无视觉反馈区别（仅按钮换文案）；结束无确认步骤（误触直接结束）；成果弹窗非组件化（手写 fixed 遮罩）；**切后台/锁屏后计时漂移**（setInterval 停走、后端按墙钟算，两边数字对不上）。
- **个人中心**：未登录/已登录无状态区分（guest 直接看到假数据兜底）；菜单 emoji+文字+`>` 文字箭头（非图标）；统计三项卡点击热区只有文字区。
- **统计页**：柱状图为手写 div（`bar-value` 悬浮 `top:-40rpx` 易裁切；高度 px 与整体 rpx 混用，跨端缩放不一致）；打卡格 30 个平铺无周分隔/月历结构；无时间范围切换；顶部大标题占位浪费（自定义导航未做返回按钮——**navigationStyle:custom 但页面没画返回键，H5 下用户困在此页**）。

## 3. 可跑性盘点

### 3.1 远程 100.77.128.110（只读探测，未动任何配置）

| 探测 | 结果 |
|---|---|
| ping | 100% 丢包（ICMP 被禁，不能证明机器下线） |
| TCP :8085 / :8082 | **均可完成三次握手**（端口有监听） |
| HTTP（/、/actuator/health、业务路径、带 Host 头） | 全部 **Empty reply from server**——请求发出后服务器 0 字节断开 |

**结论：不是"需要特定请求头"，是服务端异常**。TCP 通 + 应用层空响应的典型成因：容器/进程僵死但端口映射残留、或防火墙吞响应包。本机无从进一步判断，**需客户侧/运维登录机器查 `docker ps` 与容器日志**（红线：只读探测已尽，不自行重启）。

### 3.2 本地 docker 试跑（Apple Silicon / docker 28.0.1 / compose v2.33.1）

| 环节 | 结果 |
|---|---|
| `docker compose up mysql` | ❌ **开箱失败**：mysql:5.7.29 无 arm64 镜像（no matching manifest） |
| 强制 `--platform linux/amd64` 跑 mysql 5.7 | ✅ QEMU 模拟可跑；`sql/` 挂载初始化 **全链成功**：37 张 la_ 表、la_book 5 条、la_book_category 5 条、testuser 在库 |
| redis:7.0.4 | 未单独起（backend/frontend 起时一并验证） |
| backend / frontend 镜像构建 | ✅ 均成功（arm64 本机平台；构建 context 不含 prod 配置，采用挂载 `file:./application-prod.yml` 外部化注入） |
| 四容器联跑（mysql amd64 模拟 + redis + backend + frontend） | ✅ 全部 Up/healthy（actuator 未启用，compose healthcheck 实际无效——返回统一 404 JSON 但 HTTP 200，curl -f 判不出） |
| tester 服务 | ❌ `tests/Dockerfile` **CMD 行缺右括号**（语法不完整），镜像必构建失败 |

**配置断裂（比镜像架构更根本）**：compose 以 `SPRING_PROFILES_ACTIVE=prod` 启动，但仓库中 like-admin/like-front **均无 application-prod.yml**（根 .gitignore 明确忽略该文件名，开发者当时未提交）。无 prod 配置时 Spring 回退 application.yml 的硬编码 `localhost:3306`——容器内无 MySQL，后端必挂。**这同时解释了远程机器现状与 DAY5"六容器全绿"声称的矛盾：当时机器上存在未提交的 prod 配置，交接断层。**

（本次试跑已在本地生成带 `${MYSQL_HOST}` 等环境变量占位符的临时 prod 配置用于验证——两文件均在 gitignore 覆盖内，不会提交；正式修复属 S3。）

**nginx 路由错位**：`nginx/miniapp.conf` 将 `/api/` 全量转发 `backend:8082`（like-admin），而小程序 front 接口在 `frontend:8085`——H5 部署下小程序请求全部打错服务；`admin.conf` 同样未配底座实际使用的 `/adminapi/` 前缀（当前恰好无害，因 admin 前端请求 `api/` 前缀，但业务 controller 用 `adminapi/` 后该缺口即暴露）。

### 3.3 testuser/test123 登录链（静态分析 + 运行时实测双重实锤）

likeadmin 校验算法：`md5(password + salt)`。`sql/test_user.sql` 写入的哈希 `5f4dcc3b5aa765d61d8327deb882cf99` 是著名的 **MD5("password")**，而 `md5("test123"+"abcde") = c97871bee35d41abf34924f15f0cfb9e`。**即任何密码都无法让该测试用户登录成功**（SQL 内注释 `MD5(test123abcde)=5f4dcc...` 本身是错的）。

### 3.4 API 实测（本地四容器联跑，2026-11-02）

| # | 请求 | 结果 | 判定 |
|---|---|---|---|
| 1 | `GET :8085/api/front/bookshelf/list`（无 token） | `code 332 token参数为空` | **front 业务接口被登录拦截器全拦**：controller 未标 @NotLogin（BookshelfController import 了该注解却没用） |
| 2 | `POST :8085/api/front/bookshelf/add`、`/reading/start`、`GET /stats/overview`（无 token） | 同上 332 | 同上 |
| 3 | `GET :8082/adminapi/book/list`（无 token） | `code 200`，返回 5 本书真实数据 | **管理接口无鉴权裸奔**：任何人可 list/add/edit/delete 书籍与分类（adminapi 前缀不在底座拦截器范围）。公网部署时为高危项 |
| 4 | `GET :8082/api/admin/books/list`（test_api.py 的路径） | HTTP 200，body `code 404 No handler found` | 路径不存在实锤；且 **likeadmin 全局 HTTP 恒 200**，test_api.py 只断言 `status_code==200` 的用例会**虚假通过** |
| 5 | `GET :8085/api/api/front/bookshelf/list`（小程序实际发出的双前缀路径） | HTTP 200，body `code 404` | 小程序端所有业务请求的真实下场：404 |
| 6 | `POST :8085/api/login/accountLogin`（testuser/test123，原始哈希） | `code 314 账号或密码错误` | **登录链断**实锤（静态分析的哈希错误被运行时证实） |
| 7 | 同上（本地库修正哈希后） | `code 200` + token | 修复凭证后登录链本身正常 |
| 8 | 带 token 调 `bookshelf/list?status=1` / `stats/overview` | `code 200`，书架 2 条、统计真实数据（9.5h/连续 8 天/已读 1 本） | **后端三域业务逻辑在"配置补齐+凭证修正+带 token"前提下可用**；ReadingStatsService 字段与前端设计对齐 |

**实测总结**：后端骨架质量尚可（登录后链路通、统计计算正确）；断点全部在**集成层**——路径错位、拦截器/登录态未接入、部署配置缺失、测试凭证错误。另注意：testuser 恰好 id=1，与硬编码 userId=1 碰巧重合，**掩盖了"所有登录用户共享同一书架"的数据串号缺陷**（其他任何用户登录后操作的都是 testuser 的数据）。

## 5. 结论与 S2 输入建议

### 5.1 S1 结论

1. **功能面**：三域后端接口骨架齐（front 14 个 + admin 13 个），管理后台前端为零，小程序 6 页全为"壳或断链"，无选书入口闭环。
2. **可用性**：按当前仓库 fresh clone，**端到端无一页功能真正可用**（路径错位 × 配置缺失 × 数据解包 bug 三层叠加）。
3. **可跑性**：本地全家桶经三处 workaround 后已完整跑通并实测（arm64 用 amd64 模拟、prod 配置挂载注入、tester 语法未修未跑）；**后端三域带 token 全链可用**，断点全在集成层。远程机器服务异常需客户侧介入。
4. **欠账**：Day4/Day5 报告与实况偏差坐实，测试资产实际为零（两个文件截断 + 路径全错）。

### 5.2 给 S2 的输入

- 设计范围必须含：**底部导航与信息架构**（当前断裂）、**选书/找书入口**（当前死锁）、管理后台书籍/分类管理页（当前缺失）、底座遗留页去留清单（商城类页面建议裁撤，需 lee 定）。
- S3 除 UI 重做外需一并排期的地基项（不属设计、属整改）：路径统一（建议全走底座 `api/` 惯例）、userId 接入登录态、request 解包约定统一、testuser 哈希修正、prod 配置提交策略（或 entrypoint 生成）、mysql arm64 方案、nginx 路由修正、tests 两文件修复重写。
