## 2. 两案对比

### 甲案：裁撤（推荐）

**动作**：商城类+钱包子包+残页整目录删除（页面/组件/api/分包声明一并清），保留 git 历史。

| 维度 | 评估 |
|---|---|
| 包体 | 分包删除，主包体积降（钱包子包整包省） |
| 维护 | 无死代码负担；uni-app 编译面缩小 |
| 风险 | 删除牵连 import 关系需一次清干净（S3 做一次编译验证）；若客户后续要商城=从 git 恢复+适配（成本中） |
| 合规 | 无支付闭环的商城页留着反而有被误解为「可购物」的风险（博物馆场景尤其敏感） |

### 乙案：保留隐藏

**动作**：页面文件保留，pages.json 去注册/入口全藏（现状其实已接近此态）。

| 维度 | 评估 |
|---|---|
| 包体 | 钱包子包仍随包（未注册的分包不编译则无包体影响，但工程结构仍在） |
| 维护 | 死代码长期负债；每次全量搜索/重构都绕不开 |
| 风险 | 最低（不动代码） |
| 合规 | 风险同甲案所述（页面对外仍可达：分享码/扫码直进路由） |

## 3. 建议

**甲案（裁撤）**，理由排序：
1. 产品定位是阅读伴读（01 §1），商城/钱包与定位无交集，保留无预期；
2. 外包交付物干净度：S3 验收时「无死页」是显性质量项；
3. git 历史即恢复通道（乙案的「以后要用」成本与从 git 恢复相当）。

若客户（博物馆）明确表露商城意向（文创/图书邮购），则乙案+预留说明，等需求落地再激活——**lee 定稿时按客户意向一句话裁**。
